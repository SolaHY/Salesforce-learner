Salesforce データのインポートとエクスポート

CSV を「入れる」手段と「出す」手段を、ツールごとに色分けして図解します。 判断の軸は最後まで同じ 4 つ — 件数・対象オブジェクト・重複防止の要否・操作の種類。 この 4 つでツールが決まる、という構造で読み進めてください。

01

全体像 — 組織の外と中を行き来する 6 つの経路

Salesforce のデータ移動は、上向き（外 → 組織＝インポート）が 3 経路、下向き（組織 → 外＝エクスポート）が 3 経路。 まずこの 6 本のレーンを頭に入れると、個々のツールの説明がどこに刺さるのかが分かります。 ウィザードだけがブラウザ画面で完結し、それ以外はすべて API 層を通る、という区別が要点です。

02

03

データインポートウィザード — 重複を作らせないための道具

ウィザードの本質は「手軽さ」ではなく重複防止です。件数が小さくても、 重複を自動で弾きたいならこちらを選ぶ。逆に対応オブジェクトの狭さが最大の制約で、 商談とケースが対象外という点が引っかけとして頻出します。

対応オブジェクト

  • ○取引先
  • ○取引先責任者
  • ○リード
  • ○ソリューション
  • ○キャンペーンメンバー
  • ○個人取引先
  • ○カスタムオブジェクト
  • ×商談
  • ×ケース
  • ×ユーザ
  • ×商品・価格表

実行の流れ

  1. データの種類を選ぶ［設定］→「データインポートウィザード」→ 標準オブジェクトかカスタムオブジェクトかを選択。
  2. 処理を選ぶ「新規レコードの追加」「既存レコードの更新」「追加と更新の同時実行」から選び、照合キー（取引先責任者・リードはメール、取引先はサイト付き名称、カスタムは外部 ID など）を指定する。
  3. CSV をアップロードして項目をマッピングCSV の列と Salesforce の項目を対応づける。未マッピングの列は取り込まれない。文字コードや区切り文字もここで指定。
  4. 開始 → 結果をメールで受け取る「一括データ読み込みジョブ」画面で進捗を確認。完了後、成功・失敗件数がメール通知される。
照合キーの挙動 照合キーが一致した場合の動きは選んだ処理で変わります。「追加のみ」なら一致行はスキップ、「更新のみ」なら一致行だけ更新して新規は作らない、「追加と更新」なら一致すれば更新・なければ作成（＝ウィザード版の upsert）。 ワークフロールール・入力規則・重複ルールはウィザード経由でも発動します。
04

データローダ — 6 つの操作を色で覚える

データローダの操作は「新規に足すのか・既存を書き換えるのか・消すのか・取り出すのか」で 4 系統に分かれます。 鍵は レコード ID が必要かどうか、そして 戻せるかどうか。この 2 軸で 6 操作を整理します。

導入と実行の流れ

  1. インストール［設定］→「データローダ」からダウンロード。Windows / macOS 版があり、実行には Java 環境が必要（近年のバージョンは同梱）。API が使えるエディション（Enterprise / Unlimited / Performance / Developer など）が前提。
  2. ログインユーザ名＋パスワード＋セキュリティトークン、または OAuth で接続。信頼済み IP 範囲外からはトークンが必須。
  3. 操作を選ぶinsert / update / upsert / delete / hard delete / export のいずれかを選択。
  4. オブジェクトと CSV を指定対象オブジェクトを選び、取り込む CSV（または出力先）を指定する。
  5. 項目マッピングCSV 列と API 参照名を対応づける。マッピング定義（.sdl）を保存すれば次回以降に再利用できる。
  6. 実行と結果確認処理後に success.csv と error.csv が出力される。error.csv にはエラー理由が行単位で記録されるので、修正して再実行する。
設定：Bulk API を使うかどうか 既定は SOAP API（1 バッチ 200 件）。設定で「Use Bulk API」を有効にすると 1 バッチ 10,000 件になり、大量データが速く処理できます。 hard delete には Bulk API が必須。並列（Parallel）モードは速い一方でレコードロック競合が起きやすく、 親子関係のあるデータではシリアル（Serial）モードに切り替えるのが定石です。
05

upsert と外部 ID — Salesforce の ID を知らなくても同期できる仕組み

外部 ID（External ID）は、他システムの主キー（顧客番号など）を格納するための項目属性です。 項目定義で「外部 ID」にチェックを入れると、その項目を upsert の照合キーに使えるようになります。 これにより Salesforce 側のレコード ID を一切知らなくても、外部システムのキーだけで更新と新規作成を振り分けられます。

レコード ID の 15 桁と 18 桁 Salesforce のレコード ID には 15 桁（大文字小文字を区別する）と 18 桁（区別しない）の 2 種類があります。 Excel などは大文字小文字を区別しないため、15 桁のまま加工すると別レコードを取り違えるおそれがあります。 CSV で扱うときは 18 桁を使うのが安全です。
06

エクスポートとバックアップ — 3 つの手段の役割分担

「取り出す」目的は大きく 3 つ — 組織まるごとのバックアップ、対象を絞った抽出、 分析用のレポート出力。用途が違うので、どれか一つで済ませようとすると破綻します。

表 2 ／ エクスポート手段の比較
手段 出力 範囲 自動化 向く用途
データエクスポートサービス ZIP（CSV 群） 組織の全データ。添付・ドキュメント・Chatter ファイルも任意で含む 週次／月次のスケジュール 定期バックアップ
データローダ export CSV SOQL で指定したオブジェクト・項目・条件のみ コマンドラインで可能 移行前の退避、部分抽出
レポートエクスポート .csv（詳細のみ）／.xlsx（書式付き） そのレポートの結果行だけ 不可（サブスクリプション配信は別機能） 分析・共有用の切り出し

データエクスポートサービスの時間軸

標準機能の限界 データエクスポートサービスは「取り出す」までしか担当しません。自動で復元する機能はありません。 復元まで含めた保護が必要なら、Salesforce Backup & Restore やサードパーティ製品（OwnBackup など）を検討します。 なお、削除から 15 日以内ならごみ箱から復元でき、そこを過ぎた場合は Salesforce のデータ復旧サービス（有償・時間がかかる）が最後の手段になります。
07

実務と試験、両方で刺さる落とし穴

入力規則は API 経由でも効く IMPORT

データローダや API 経由の書き込みにも入力規則・必須項目・重複ルールが適用されます。大量インポートで一斉にエラーが出るのは典型例。事前に規則を確認し、必要なら一時的に無効化して、完了後に必ず戻します。

読み取り専用でも防げない SECURITY

ページレイアウトで項目を読み取り専用にしても、データローダや API からの更新は止まりません。確実に守るなら項目レベルセキュリティか入力規則を使います。

親 → 子の順に取り込む ORDER

参照関係／主従関係があるデータは、親レコードを先に作らないと子が紐づきません。親の外部 ID を子の CSV に載せておけば、Salesforce のレコード ID を知らなくても関連付けできます。

文字コードと日付書式 CSV

日本語データは UTF-8 で保存する（Excel の既定のままだと文字化けしやすい）。日付はユーザのロケール設定に従うため、YYYY-MM-DD に揃えておくと事故が減ります。

所有者と自動割り当て OWNER

Owner ID 列を省くと、インポートを実行したユーザが所有者になります。リードの割り当てルールなどを効かせたい場合は、ウィザード側でチェックを入れる必要があります。

自動化が一斉に発火する AUTOMATION

インポートはワークフロー・フロー・トリガ・メール通知を起動します。数万件を一度に流すと大量のメールや処理が走るため、事前に対象の自動化を洗い出しておきます。

API コール数の消費 LIMIT

データローダは API を消費し、組織には 24 時間あたりのコール数上限があります。SOAP（200 件／バッチ）より Bulk API（10,000 件／バッチ）のほうが消費を抑えられます。

本番前にサンドボックスで SAFE

まず数十件のサブセットで試し、error.csv を確認してから全件を流します。update / delete の前には対象を export しておくと、失敗時に元へ戻せます。

インポート前チェックリスト

  • CSV は UTF-8、1 行目は列見出し、区切り文字は統一されているか
  • マッピング先の API 参照名を確認したか（表示ラベルではなく API 参照名で対応づける）
  • 更新・削除の対象を事前に export してバックアップを取ったか
  • レコード ID は 18 桁で揃えたか
  • 親レコードが先に存在しているか、または外部 ID で参照解決できるか
  • 入力規則・重複ルール・トリガの影響範囲を確認したか
  • まず少量で試験実行し、error.csv を確認したか
  • hard delete を使うなら「一括削除」権限と Bulk API を有効にしたか
08

試験ポイントの総ざらい

数字と例外はそのまま出題されます。太字部分が答えになりやすい箇所です。

  1. 01インポートウィザードの上限は 1 回あたり 50,000 件。データローダは 最大 500 万件。
  2. 02ウィザードが対応するのは取引先・取引先責任者・リード・ソリューション・キャンペーンメンバー・個人取引先・カスタムオブジェクト。商談とケースは対象外。
  3. 03重複防止ができるのはウィザードだけ。データローダは upsert の照合キーを使わない限り単純追加になる。
  4. 04データローダは すべてのオブジェクトに対応し、削除・抽出・upsert もできる。ウィザードは追加と更新のみ。
  5. 05update には レコード ID が必須。ID の無い行はエラーになる。
  6. 06upsert は照合キーが一致すれば更新、なければ挿入。照合キーには レコード ID または外部 ID を使う。
  7. 07外部 ID は他システムの主キーを保持する項目属性。upsert の照合キーにするには一意である必要がある。
  8. 08delete はごみ箱へ移動（15 日以内は復元可）、hard delete は復元不可。
  9. 09hard delete の実行には 「一括削除」権限の付与と Bulk API が必要。既定では実行できない。
  10. 10export は有効なレコードのみ、export all は 削除済み・ごみ箱内も含む。
  11. 11データエクスポートサービスは ZIP 形式の CSV 群で組織の全データを出力する。
  12. 12エクスポート頻度は Enterprise / Unlimited / Performance が 週次または月次、それ以外は 月次のみ。
  13. 13生成されたエクスポートファイルの保持期間は 48 時間。
  14. 14レポートエクスポートは 「詳細のみ（.csv）」と「フォーマット済み（.xlsx）」の 2 形式。組織全体のバックアップには不十分。
  15. 15入力規則・必須項目・重複ルールは データローダや API 経由の書き込みにも適用される。
  16. 16ページレイアウトの読み取り専用は API 経由の更新を防げない。
  17. 17レコード ID は 15 桁（大文字小文字を区別）と 18 桁（区別しない）。CSV では 18 桁が安全。
  18. 18データローダは API を消費する。ウィザードは画面処理なので消費しない。
  19. 19Bulk API 使用時のバッチサイズは 10,000 件、SOAP API では 200 件。
  20. 20データローダは 設定を保存してコマンドラインで定期実行できる。ウィザードは毎回手動。
